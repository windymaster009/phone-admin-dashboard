# PhoneFlow two-factor authentication

PhoneFlow supports time-based one-time passwords (TOTP) for `OWNER` and `MANAGER` accounts.

## Server setup

Generate a dedicated 32-byte encryption key once:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

Store the result in the server environment:

```env
TWO_FACTOR_ENCRYPTION_KEY=<generated base64 key>
```

Do not reuse `JWT_SECRET`. Do not commit this key. Back it up separately from the database.

The key encrypts authenticator secrets with AES-256-GCM. Losing or changing it makes already-enrolled authenticator secrets unreadable.

## Enabling 2FA

1. Sign in as Owner or Manager.
2. Open **Finance & Control → Security**.
3. Choose **Set up 2FA**.
4. Add a time-based account in an authenticator application using the displayed setup key or copied `otpauth://` setup link.
5. Enter the six-digit code generated by the authenticator.
6. Save the recovery codes immediately.

Enabling 2FA revokes all other sessions for that account. The current session is marked as 2FA verified.

## Sign-in flow

For an enrolled account:

1. Email and password are verified first.
2. No authenticated session is created yet.
3. PhoneFlow creates a short-lived server-side 2FA challenge.
4. The user enters a six-digit authenticator code or one recovery code.
5. Only after successful verification is the real revocable session created.

The challenge expires after five minutes and is blocked after five invalid code attempts. The verification endpoint also has rate limiting.

## Recovery codes

PhoneFlow creates ten recovery codes when 2FA is enabled.

- Each recovery code works once.
- Only keyed hashes are stored in MongoDB.
- Plain recovery codes are shown only immediately after generation.
- Regenerating recovery codes invalidates all previously saved codes.
- Using a recovery code is written to the security activity log.

## Android pairing

If the account has 2FA enabled, Android pairing must be created from a session that has already passed 2FA. The paired Android session inherits that 2FA-verified state.

The old private-LAN automatic Owner login remains disabled.

## Disabling 2FA

Disabling 2FA requires a currently valid authenticator or recovery code. PhoneFlow revokes all other sessions after the change.

## Backup and restore

The permanent 2FA credential is encrypted in MongoDB and therefore included in the normal database backup. The `TWO_FACTOR_ENCRYPTION_KEY` is not in the backup and must be preserved separately.

Short-lived session, pairing, setup, and login-challenge collections can also appear in a general backup. TTL indexes expire them normally. For a restored production database, revoke active sessions before reopening the restored instance to staff traffic.

## Manual verification checklist

1. Configure `TWO_FACTOR_ENCRYPTION_KEY` and restart the server.
2. Enable 2FA for an Owner account.
3. Confirm a valid authenticator code enables the feature.
4. Sign out and sign in again; confirm password alone does not create a session.
5. Confirm an invalid TOTP is rejected.
6. Confirm a valid TOTP creates a session marked 2FA verified.
7. Sign in with one recovery code and confirm its remaining count drops by one.
8. Try that same recovery code again and confirm it is rejected.
9. Regenerate recovery codes and confirm old codes stop working.
10. Pair Android from a 2FA-verified browser and confirm the Android session is marked 2FA verified.
11. Disable 2FA using a current code and confirm other sessions are revoked.
12. Run `npm run lint`, `npm test`, and `npm run build`.
